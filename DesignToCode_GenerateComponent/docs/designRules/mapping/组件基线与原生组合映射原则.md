# 组件基线与原生组合映射原则

本文维护已确认的目标与组合原则。候选核对矩阵不是当前组件清单；现行公共身份读取 Registry/Contract/Runtime Mapping，数量与历史阶段结论见归档。

## 1. 已确认的核心目标

**一阶段组件范围 = Qt 原生组件能力 ∩ Ant Design 中包含的设计组件。组合能力必须严格遵循 Qt 原生组件能力构造。**

目标是在这个范围内建立较完整的设计侧到开发侧组件及组合映射方案，使 GenerateLayout 在生成页面时能够有效识别组件、正确应用参数，并保持行为与视觉一致。后续范围、实现和验收调整以本节用户确认的说明为纲领；影响该目标或需要改变原生能力边界的问题，先向用户确认。

用户指出当前比较完整的基础为 Button、InputField（LineEdit）、DropdownMenu、Checkbox，这个范围不足以完成一阶段基线。四项是现有起点，不是一阶段范围上限。现有工程文档还单独登记了 `Z_Select`；DropdownMenu 与 Select 的关系需要按命令菜单、值选择两种语义分别核对，不能用一个名称替换另一个。

“交集”按设计组件语义与原生能力判断，不按类名字符串求交，也不要求一个设计组件只能对应一个 Qt 类。一个设计组件可以使用多个 Qt 类型；多个 Qt 类型也可以服务于同一设计组件族。Layout、Model、Action、Validator、Delegate 等属于组合支撑能力，不因此各自新增一个设计组件计数。

原生组件数量、SDK 工厂注册项数量、Ant 设计组件族数量、已完成映射数量分别统计。59 个 Qt 包装类型或 62 个 SDK 注册项，不能直接作为一阶段组件范围或完成数量。

## 3. 严格遵循原生能力的组合策略

按以下三种情况记录每项需求，避免把可继承、需组合和缺能力混写：

| 情况 | 构造方式 | 必须提供的依据 |
| --- | --- | --- |
| 单个原生类型能够承担核心语义 | 使用已有 SDK 包装或语义组件，复用原生行为，映射设计属性与 Token | Qt 基类、公开接口、状态与设计身份 |
| 多个原生类型共同承担语义 | 明确组件树、数据关系、布局、信号和生命周期，封装为可复用 SDK 组合 | 每个组成类型的职责、公开连接方式及组合行为测试 |
| 原生或现有公开扩展不能满足要求 | 记录差异及能力缺口，向用户确认后决定支持边界 | 缺失能力、影响属性/状态及可能的原生扩展途径 |

继承、组合及 Qt 正式扩展点可以用于实现，但必须指出所依赖的真实能力。不能因为 Qt 可以自绘就把任意 Ant 组件宣称为交集；新增绘制或行为也不能冒充 Qt 默认行为。自绘仅在职责明确且经确认的扩展内使用，保留原生输入、焦点、模型和生命周期机制。

组合合同至少描述：组件身份、组成类型、语义槽位、布局关系、数据/选择模型、状态来源、公开参数与信号、资源、Token 消费位置、对象所有权、生效顺序，以及不支持项。

组状态必须有确定来源。例如 Checkbox 组的 mixed 由子项集合推导，Radio 组使用原生互斥关系，Table 的行选择与单元格勾选分开，Dropdown 的 Action 触发与 Select 的值变化分开。布局生成器不能独立重写这些规则。

## 4. 组件交集的初步核对矩阵

以下是基于现有目录与参考资料整理的候选关系，不是已批准的最终清单，也不是完成状态。先覆盖完整候选范围，再逐族核定支持属性与状态；分批实现不减少一阶段最终范围。

### 4.1 有明确原生起点的组件族

| 设计组件族 | Qt 原生起点或支撑类型 | 需核定的语义边界 |

| Button | QPushButton、QToolButton、QAbstractButton | 类型、图标、加载、禁用和原生点击路径 |
| Input / TextArea | QLineEdit、QPlainTextEdit；QTextEdit 按富文本需求核定 | 单行、多行、只读、校验反馈及内容接口 |

| Radio | QRadioButton、QButtonGroup | 互斥、组值、键盘与禁用传播 |
| Dropdown | QToolButton 或 QPushButton + QMenu + QAction | 命令身份、触发方式、子菜单与弹出生命周期 |
| Menu | QMenu、QMenuBar、QAction | 原生命令菜单与页面导航菜单的差异 |

| InputNumber | QSpinBox、QDoubleSpinBox | 范围、步长、精度、输入与值变化 |
| Slider | QSlider | 拖动值、方向、刻度及单值范围；双端范围另核定 |
| DatePicker / TimePicker | QDateEdit、QTimeEdit、QDateTimeEdit、QCalendarWidget | 单值、范围、格式、弹出与禁用日期能力 |

| Progress | QProgressBar | 确定/不确定进度；圆环展示能力另核定 |
| Tabs | QTabWidget；QTabBar + QStackedWidget | 当前项、切换、关闭与内容生命周期 |

| Tree | QTreeView、模型、选择模型、委托 | 展开、选择、勾选及数据重置 |
| List / Listy | QListView、模型、委托 | 数据规模、视图能力与对应版本要求 |
| Modal | QDialog、QDialogButtonBox；QMessageBox 按用途选用 | 模态、确认/取消、关闭与业务动作 |

| 设计组件族 | 候选原生构造路线 | 纳入前必须验证 |
| --- | --- | --- |
| Form | QWidget + QFormLayout + 已支持字段组件及标签 | 字段身份、值接口、提示与业务校验边界 |
| AutoComplete | QLineEdit + QCompleter + 模型 | 补全显示、选择回写与异步数据归属 |
| TreeSelect / Cascader | 输入/触发器 + 树或列视图 + 模型 + 弹出容器 | 选择路径、值语义、弹出行为与焦点 |
| Transfer | 两侧列表视图 + 模型 + 操作按钮 + 布局 | 两侧数据关系、移动规则与选择状态 |
| Pagination | 按钮 + 数字输入/选择控件 + 标签 + 布局 | 页码状态、总数/页大小与请求事件分工 |
| Segmented / Switch | 可勾选原生按钮及组关系 | 选择/开关语义、键盘和反馈；不能只换外观 |
| Card / Descriptions | QFrame 或 QGroupBox + 布局 + 内容组件 | 容器职责、标题、插槽及尺寸规则 |
| Collapse / Steps | QToolBox 或显式原生容器组合；向导场景参考 QWizard | 折叠与步骤导航的独立语义；不直接等同原生类 |
| Tooltip / Popover / Popconfirm | QToolTip 或原生弹出容器 + 标签/按钮 | 非交互提示与交互浮层的差异、定位、焦点和关闭 |

| Drawer | 原生容器/窗口与布局；QDockWidget 仅作可核对起点 | Dock 与覆盖式抽屉不等价，需证明定位与关闭行为 |
| Upload | QFileDialog + 列表/进度/按钮组合 | 文件选择只是其中一步；传输、权限与服务归业务 |
| Flex / Grid / Layout / Space / Divider | Qt Layout、容器与QFrame等结构能力 | 进入布局规则或组件合同的边界、伸缩及明确间距 |

以上新增支撑类型仍需在项目能力目录登记和目标 Qt 上核验；列出候选不等于现有 SDK 已提供。每族支持到哪些属性，必须通过后续合同确定，不能默认为覆盖 Ant 全部能力。

其余总览条目仍要登记纳入、待核定或不纳入的理由，特别是依赖专用绘制、编码、动画、浏览器上下文的 Rate、QRCode、Carousel、Tour、Watermark、Skeleton、Spin、Avatar、Badge、Tag、Timeline、Anchor、Breadcrumb、FloatButton、Masonry、Mentions、Affix、BorderBeam 等。App、ConfigProvider、Util 属于上下文/配置或工具语义，不能按 QWidget 包装计作可视组件。Pro 系列单独判断，不自动并入基础交集。

现有能力目录有 52 个可视 Qt 类型带 Ant 参照关系，但这是 Qt 类型行数。`QStatusBar → App`、`QDockWidget → Drawer`、`QFileDialog → Upload` 等必须重新核定实际语义；这些历史标签不能直接批准一阶段范围，也不能依据其数量计算覆盖率。

## 5. 设计到工程的统一映射合同

每个范围内组件族建立同一结构的记录，沿用现有事实源，避免再建一套平行 Token 或组件工厂：

| 合同部分 | 必须留下的内容 | 消费位置 |
| --- | --- | --- |
| 范围和身份 | 设计语义、提供方、文件/组件集/变体身份、证据版本、支持子集 | 设计证据与组件映射 |
| 原生能力 | 基类/组合类型、Qt 版本、真实属性/API/模型角色及限制 | GenerateComponent |
| 组成与槽位 | 根组件、内部角色、文本/图标/内容槽、允许替换项 | SDK 组合实现与设计适配 |
| 参数与值域 | 类型、单位、默认值来源、枚举、必填项、非法组合 | 合同校验、工厂与公开 API |
| 状态和事件 | 初始化状态、原生瞬时状态、业务输入状态、信号与转换规则 | SDK 与业务接入 |
| Token 和资产 | Variable 到 Token 的对应、Profile、消费部件、前景背景配对及资源身份 | Token 编译、QSS/运行参数/资源 |
| 页面接入 | `.ui` 可表达字段、代码配置、生效顺序、公开 getter 和 SDK 依赖 | GenerateLayout |
| 验证和发布 | 实际命令、输入/产物哈希、交互/几何/视觉结果、缺口及兼容记录 | ComponentLab 与 SDK 消费测试 |

设计适配读取经过验证的 Canonical 工程合同；Raw 留作审计。当前 Figma 输入必须使用真实身份，不用显示名称或拼接值冒充原生 key。设计层级与内部 Qt 对象不要求逐层一一对应，映射要说明哪些是组件职责、哪些是页面布局职责。

稳定视觉值从批准的 Token 源进入编译链；文本、选项、命令标识等实例参数进入组件合同；业务数据、权限和请求处理留在业务侧。缺字段与显式 0 区分，未知身份、非法值域、断裂引用或缺能力明确失败。明确但尚未证明 Token 绑定的值继续按既有规则记录缺口，不用猜值补齐。

## 6. 三个工程如何保障 GenerateLayout 一致性

1. GenerateComponent 维护原生能力、组件族合同、组合实现、Token 编译与 SDK 发布；同一设计语义只使用已核定的公开实现路径。
2. ComponentLab 按设计组件族验收属性、状态和组合，再单独展示各 Qt 包装类型。不能只以工厂实例化证明映射完成。
3. GenerateLayout 按身份和支持值域选择 SDK 组件，编译结构与公开参数调用；不复制内部组件树、状态机或私有适配器作为第二实现。
4. 正式页面继续采用现有 `uic` 页面包合同（ui/h/cpp/qss/qrc）。页面访问 SDK 公开能力，组件内部对象不逐层展开成页面 XML；复杂表格的数据通过模型和列键接入。
5. 消费端使用明确且相容的 SDK、映射和 Token 版本。已有 Compact 三页作为回归证据，不能替代新组件覆盖和组合验收。

当前页面交付默认采用 `standard-light`。组件的 Compact/Comfortable 密度不映射为 Profile；四个合法上下文为 `standard-light`、`standard-dark`、`wide-light`、`wide-dark`。页面侧验收范围仍按实际需求和测试记录确认。

## 7. 一阶段完成标准与下一步

一阶段需要先核定整个交集范围，再逐项完成，不以四个基础组件或一个业务页面替代整体基线。分批实施只表达依赖顺序。

每个纳入组件族同时满足以下条件才标记完成：

1. 真实设计身份、组成、属性、状态与支持子集可以定位和复核。
2. Qt 原生能力及组合关系明确；不支持项没有被静默降级。
3. 设计参数到公开 API/模型/布局的转换可校验，非法输入有可定位结果。
4. Token 与资源可重复生成，适用配置下的状态及组合行为经过验证。
5. SDK 独立消费者可构建运行，ComponentLab 能展示本族完整验收范围。
6. GenerateLayout 能正确引用和配置该族，在组合案例中保持语义、几何与状态一致；视觉结果按明确条件确认。

统计同时列出总范围、已完成、待完成、被阻断以及待范围核定项。不能因某族难实现就自行从分母删除，也不能把“待核定”写成已支持。
