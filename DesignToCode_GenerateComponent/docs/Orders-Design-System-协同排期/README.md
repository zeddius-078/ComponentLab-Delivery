#### 首批重点组件范围

本轮不同时改造全部 41 项组件。首批选择能够代表基础操作、选择状态、表单输入和数据展示的典型组件，并直接进入规范整理、Token 接入和各平台实际改造：

- 按钮族，包含状态按钮以及所有单击一次即可触发操作的交互组件；
- 单选框；
- 勾选 / 复选框；
- 文本输入框，作为参数配置行和其他表单的基础输入组件；
- 下拉选择器，用于从选项中选择一个值；
- 参数配置行，由参数名称、当前值、输入控件和操作组成；
- 表格族，同时包含数据浏览表格和可编辑表格。

首批范围集中在项目中重复使用、样式问题较多且容易影响整张页面一致性的基础控件和复合表单。实施时直接按 UCD 规范补齐状态、Token 接入和平台实现。其他组件形成后续改造任务，本轮不展开实际修改。

状态按钮作为按钮族的一种类型，不单独计算为新的组件种类。按钮族内部通过类型、状态和使用场景区分。参数配置行和表格未直接出现在当前 41 项清单中，作为本项目补充的两个复合组件族记录；不改写原 UCD 41 项清单本身。

下拉选择器属于选择类组件，需要检查关闭、展开、悬浮、选中、禁用和错误等适用状态。它与点击后显示操作命令的下拉按钮分开管理。

参数配置行属于复合组件，一条参数配置行至少包括：

- 参数名称或参数行名称；
- 当前值；
- 用于填写设定值的输入框、下拉选择器或其他输入控件；
- 设定参数值；
- 按钮或其他操作功能。

完整参数配置表单由多条参数配置行组成，作为组件组合和页面使用模板管理，不重复计算为新的组件。改造和验收时需要分别处理完整表单模板、参数配置行及行内基础控件，不能只修改输入框的视觉样式。

表格按一个组件族管理，当前包含两种主要模式：

- 数据浏览表格：用于展示、筛选、选择和执行行操作；
- 可编辑表格：允许直接修改单元格或行内参数，并处理校验和提交结果。

两种模式共享表头、行、单元格、选择和页面状态等基础结构；可编辑表格另外检查编辑、校验、修改和提交相关状态。具体功能数量较多，需要在后续任务中确定首轮检查边界。

当前决定已锁定：表格按照一个组件族管理，不再拆成两套互不关联的组件。具体功能和状态数量留到实施拆分阶段确定，本轮任务梳理不再继续展开。

### 3.6 Figma 与 Pixso 的使用分工

- Pixso 是设计规范、Token、组件库的主要生产、复用和交付工具。
- Pixso 中的正式资产作为当前设计端主要生产、复用和交付载体，但不能取代 UCD 规范文件的规则来源地位。
- Figma 只承担辅助作用，用于参考、竞品分析、基础绘图和变量方案试验。
- Figma 中的试验内容不能自动视为正式规范，需要确认后再进入 Pixso 生产资产。
- Pixso 负责设计端编辑、评审和确认；确认后的标准 Token JSON 进入统一工程仓库，作为各开发平台唯一可发布的 Token 数据源。
- PyQt、PySide2、C++ Qt、Vue2 和 Vue3 不各自维护一套 Token 数值，只维护各自的转换规则和生成结果。

工程发布链统一为：

```text
UCD 规范
→ Pixso 设计和确认
→ 标准 Token JSON
→ 校验与转换脚本
→ PyQt / PySide2 / C++ Qt / Vue2 / Vue3 生成文件
→ 组件和页面使用
```

该方案同时支持两类工作：

- 新界面建设：从已确认的视觉稿、Token 和组件规范生成平台可用的样式与代码数据，开发直接使用统一组件和生成文件；
- 已有界面整改：在实际修改时扫描原有 raw 值和旧样式，将能够确认语义的内容替换为 Token，并输出无法自动判断的项目和修改前后对比结果。

以上两类用途已经确认，后续平台方案和任务拆解必须同时覆盖，不能只提供新界面生成能力，也不能只做旧界面替换工具。

生成过程必须可追溯。每次生成都要记录标准 JSON 版本、生成器版本、目标平台、Theme/Profile、Token 到生成属性的对应关系、未支持项和错误信息。生成文件不得手工修改。

转换脚本负责稳定数值、已知属性和已定义组件状态的转换，但不能自动判断业务语义、重新设计组件结构、修复复杂自绘图形或代替人工视觉验收。这些问题仍由组件规范、平台实现和验收共同处理。

### 3.10 当前缺少的界面密度规则

界面密度不是屏幕分辨率、PPI 或整体缩放倍率。它表示在同一个可用区域内安排多少信息，以及控件、表格行、参数行、工具栏、间距和留白之间有多紧凑。

交互尺寸回答“控件至少多大才能安全操作”，字号回答“文字多大才能清楚阅读”，界面密度则回答“在不破坏操作和阅读的前提下，一屏应该放多少内容”。当前项目已经有前两类数值，但尚未形成界面密度规则。

当前决定是不从零建立完整密度体系，而是采用成熟公开规范作为基线，再映射到现有 UCD 规范和工业软件场景：

- IBM Carbon 作为桌面高信息密度、Spacing、栅格和数据表格尺寸的主要参考；
- 华为设计规范作为 vp、触控尺寸、间隔和多设备响应式规则的补充参考；
- Apple Human Interface Guidelines 只参考内容分组、视觉层级、留白和适应性原则；
- 不直接复制其他品牌的颜色、图标、组件外观和专有资产。

IBM Carbon 是开源设计系统；Apple 和华为属于公开官方设计指南，不等同于可整体复制的开源组件库。本项目只引用其公开规则和实践，并转换为 UCD 规范下的表达。

**每个试点必须补齐的两类规则**

试点中的每一类界面内容都必须同时留下 Token 化规则和 AI 交付规则，不能只保留最终代码或截图。

两类规则统一按以下七个部分编写，PyQt 和 C++ Qt 两个试点使用同一结构：

1. **页面结构、布局、间距和密度**：页面区域、布局关系、Spacing、尺寸档位、Profile 和密度选择；

4. **复合组件与组合方式**：参数配置行、完整表单、数据浏览表格、可编辑表格及其内部组件关系；
5. **Icon、图片和插画资产**：Icon Token、资源索引、文件引用、替换规则及业务线资产与集团资产的对应关系；

**AI 和转换脚本修改文件的规则**

文件按照“自动生成”或“人工维护”两种归属处理：

- 自动生成的 QSS、CSS、Token 模块、资源索引等文件，可以由转换脚本重复覆盖，但需要明确生成来源和版本，且不能再由人工单独维护其中的数值；
- 人工维护的 `.ui`、Python、C++、Vue 页面和组件文件，AI 与转换脚本只能先输出修改差异、独立副本或独立分支，不能直接无提示覆盖；
- `.ui` 或其他文件如果在具体项目中已经明确属于全量自动生成文件，则按自动生成文件处理；否则一律按人工维护文件处理；
- 人工维护文件只有在查看修改内容、运行相关检查并确认结果后才能合入；
- 每次修改必须能够找到修改前版本，并能够撤回本次修改。

以上规则不要求建立复杂审批流程。小组只需要在实际合入前看清改动、运行必要检查并及时处理发现的问题。

**每次 AI 交付的最小结果集**

以上五项用于说明 AI 实际做了什么以及结果是否可信，不增加负责人、影响等级和复杂审批字段。缺少实际运行结果时，不能把 AI 生成内容写成已经验证完成。

### M4 从 Token 重新生成并复查三个平台

**当前状态：名称、两轮验证方法、检查范围和完成判断均已锁定。**

**阶段目标**

证明 M3 的结果不是一次性手工修改，而是能够从同一套 Token 和规则重复生成、检查、修改并恢复。

**输入**

- M2 确认的标准 Token、Schema、Profile、首批组件和 Icon 资产；
- M3 的 PyQt、Vue2、C++ Qt 转换脚本和生成文件；
- 一个 PyQt 真实业务试点和一个 C++ Qt 真实业务试点；
- M3 七个部分的 Token 化规则、AI 交付规则和五项最小交付结果；
- 本轮使用的环境、命令和基线截图。

**第一轮：从干净状态重新生成**

1. 固定 Token、转换脚本、项目代码和运行环境版本；
2. 清理可以安全重建的自动生成文件，不删除或覆盖人工维护文件；
3. 从标准 Token 重新生成 PyQt、Vue2、C++ Qt 的目标文件；
4. 重新构建并运行三个平台的首批组件；
5. 重新运行 PyQt 和 C++ Qt 两个业务试点；
6. 检查组件状态、布局、Icon、页面效果和业务操作；
7. 记录生成文件、修改差异、命令结果、截图和未解决问题。

**第二轮：受控修改并恢复**

1. 选择一个能够被三个平台共同消费的已确认 Token；
2. 对该 Token 做一次明确、可识别的临时修改；
3. 重新生成三个平台文件并检查预期位置是否发生正确变化；
4. 检查未使用该 Token 的内容是否保持不变；
5. 恢复 Token 原值并再次生成；
6. 确认生成文件、组件和两个业务试点恢复到第一轮基线；
7. 记录修改、传播范围、恢复结果和异常。

两轮均使用 M3 确认的文件修改规则：自动生成文件可以重建，人工维护文件只通过差异或独立副本确认，不直接无提示覆盖。

**AI 辅助**

AI 可以重跑命令、整理生成差异、执行截图对比、发现异常并生成验证记录初稿。AI 不能自行决定业务操作是否正确，也不能独立给出最终完成结论；组件效果、交互结果和业务可用性仍由小组实际确认。

**问题与实践过程记录**

M4 发现任何问题时，先保留问题发生时的输入版本、命令、界面或日志证据，再开始修改。每次修正后记录实际改动和重新执行结果。失败尝试、没有生效的修改和回退过程同样保留，不能只呈现最终成功截图。

**完成判断**

M4 同时满足以下五项才计为完成：

1. PyQt、Vue2、C++ Qt 都能从固定版本 Token 重新生成并运行；
2. 受控 Token 修改只影响预期位置，没有无法解释的额外变化；
3. 恢复 Token 后，生成文件、组件和界面能够回到第一轮基线；
4. PyQt、C++ Qt 两个业务试点的关键操作正常，Vue2 首批组件能够正常使用；
5. 命令结果、文件差异、截图、问题处理过程和回退记录完整。

发现问题后先记录，再修正并重跑对应步骤。当前小组不建立“有条件通过”流程；五项未全部满足时，M4 继续处理，不计为完成。
